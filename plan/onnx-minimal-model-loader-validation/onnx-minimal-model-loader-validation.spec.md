# onnx-minimal-model-loader-validation Specification

## Acceptance Criteria

1. `tests/model_runtime/model_pool/fixtures/build_minimal_identity_model.py` creates
   the committed `minimal_identity.onnx` deterministically using the existing
   `onnx==1.16.2` baseline. Its `--check` mode does not write and fails if the committed
   bytes do not match generated bytes.
2. A real `_OnnxModelLoader` consumes the committed artifact and returns an object for
   which `isinstance(session, onnxruntime.InferenceSession)` is true and
   `session.get_providers() == ["CPUExecutionProvider"]`.
3. Runtime evidence invokes neither `InferenceSession.run()` nor any Executor/invoker;
   parse/session creation plus provider metadata is the whole claimed semantic.
4. Non-ONNX bytes pass through the real `_OnnxModelLoader`; the test only establishes
   `type(error).__module__.startswith("onnxruntime.")`, without monkeypatching the
   Loader/provider or coupling to an exception message/class.
5. `test_onnx_local_runtime_acquisition.py` uses the committed valid artifact while
   retaining async offload, cancellation, options-rejection, and provider-failure
   evidence. `test_local_runtime_composition.py` remains ReadOnly regression evidence
   for PICKLE/TORCH fail-closed behavior.
6. Dedicated strict Pyright includes only the fixture generator and
   `tests/typecheck/onnx_minimal_model_loader_validation.py`; that witness imports no
   `onnxruntime`, accepts the Loader result as `_OnnxRuntime`, and the only config
   diagnostic override is `reportPrivateUsage: "none"`.
7. Production `_OnnxRuntime`, Loader return annotation, production code, dependency
   manifest/lockfile, global Pyright config, public APIs, and release metadata remain
   unchanged.

## Behavioral Scenarios

### Scenario 1: Committed minimal model provides real Loader evidence

- **Given**: `minimal_identity.onnx` equals normal output of the fixed generator and
  `onnxruntime==1.22.0` is available in the dev environment.
- **When**: a test constructs an ONNX `ModelArtifact` pointing at the committed asset
  and awaits `_OnnxModelLoader().load(artifact)`.
- **Then**: the result is a genuine `onnxruntime.InferenceSession` configured only with
  `CPUExecutionProvider`; the test observes metadata only and never calls `run()`.

### Scenario 2: Invalid bytes preserve provider ownership of failure

- **Given**: a temporary path containing non-ONNX bytes and an ONNX `ModelArtifact`
  pointing at that path.
- **When**: the real `_OnnxModelLoader` loads it without importer/provider replacement.
- **Then**: a real exception is raised and the test asserts only that its type module
  starts with `onnxruntime.`.

### Scenario 3: Static witness stays at the production Protocol boundary

- **Given**: the topic-local strict Pyright project containing only the generator and
  a witness that imports `_OnnxModelLoader` and `_OnnxRuntime`.
- **When**: the witness awaits the Loader and supplies its result to an
  `_OnnxRuntime`-typed helper.
- **Then**: strict checking succeeds without importing `onnxruntime`, without source
  suppressions/`Any`/`cast`, and without changing production annotations.

## Error / Edge Cases

- `--check` sees a byte mismatch: it exits nonzero and leaves the committed asset
  unchanged; it must not silently regenerate the binary.
- The provider's invalid-model exception type/message can vary: tests must not assert
  either; only the `onnxruntime.` module origin is stable for this topic.
- `onnxruntime` has no stubs at `1.22.0`: real runtime pytest files must not become
  dedicated strict Pyright targets. This is not permission to weaken global Pyright or
  the production `_OnnxRuntime` return contract.
- Existing cancellation/offload behavior remains unchanged: the topic asserts current
  regression coverage rather than introducing timeout/retry/lifecycle semantics.
- PICKLE/TORCH regression coverage remains in its existing ReadOnly test; no runtime
  family routing or composition change is permitted.
